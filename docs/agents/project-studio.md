# Working with the Project Studio agents

This repository is worked by a team of agents (reviewer, product, developer, qa, lead, designer) scheduled by Paperclip, and by people. Everything the team does is visible here: issues, labels, comments and pull requests. This file is generated by `studio apply`; edit `studio.yaml` in the Project Studio repository instead of this file.

## Who does what

| Step | Who | Signal |
| --- | --- | --- |
| Reviews every pull request before QA | reviewer agent | posts a `## Review` comment, adds `reviewed` for QA or sends it back with `qa-failed` (at most 2 rounds that request changes, then `asaf-shitrit`) |
| Proposes features | product agent (weekly) | files an issue labelled `needs-triage`, `enhancement` |
| Keeps the roadmap | product agent (weekly); anyone can comment on it or edit it | rewrites the pinned `Roadmap` issue (labelled `roadmap`) and keeps every human edit; one comment per cycle says what moved |
| Triages new issues | company triage agent (three times a day), or anyone with triage access | moves `needs-triage` to `ready-for-agent`, `needs-info` or `wontfix` with a `## Triage decision` comment, and escalates only high-risk items to `asaf-shitrit` with `ready-for-human`; a person's label always wins |
| Implements an approved issue | developer agent | adds `claimed`, opens a pull request labelled `needs-qa` with `Fixes #N` |
| Verifies the pull request | qa agent | posts `## QA round N`, swaps `needs-qa` for `qa-passed` or `qa-failed` (at most 2 failed rounds) |
| Reviews and merges | lead agent, or anyone with write access | approves on GitHub and merges (`squash`) when the change is small enough; otherwise labels `ready-for-human` |
| Decides what the agents could not | `asaf-shitrit`, or anyone with write access | items labelled `ready-for-human` and assigned to `asaf-shitrit` |
| Keeps the company roadmap across repos | company CEO agent | the pinned `Roadmap` issue in `asaf-shitrit/project-studio`; it may leave `## CEO note` comments on this repo's roadmap |
| Housekeeping across repos | company cleanup agent (daily) | releases stale claims, deletes merged `agent/*` branches, closes issues whose pull request merged; never changes code |

## Labels

Issues carry one triage label at a time:

- `needs-triage`: nobody has looked at it yet.
- `needs-info`: waiting on the reporter.
- `ready-for-agent`: fully specified; the developer agent may take it. Only set this when the issue says what done looks like.
- `ready-for-human`: needs a person to implement or decide.
- `wontfix`: will not be done.

Handoff labels say who holds an item:

- `claimed` (issue): the developer agent is on it. A claim older than 24 hours with no pull request is stale; remove the label to free it.
- `needs-qa` (pull request): waiting for the reviewer, then for the QA agent.
- `reviewed` (pull request): the reviewer checked it; QA picks it up.
- `qa-failed` (pull request): a review or a QA round found problems; the developer agent picks it up again.
- `qa-passed` (pull request): QA passed; the lead agent or a person can merge.
- `ready-for-human` (issue or pull request): the agents stopped; a person decides. Comments starting with `Escalated to a human` say why.

## Doing it yourself

- To hand an issue to the agents: make sure the body says what should be true afterwards, then add `ready-for-agent`.
- To keep an issue for people: add `ready-for-human`.
- To review or merge a `qa-passed` pull request yourself: go ahead; the lead agent skips pull requests that are already merged or that carry `ready-for-human`.
- To stop the agents on one item: add `ready-for-human`. To stop them on everything: pause the routines in Paperclip.

## Goals

The goals that shape what the agents propose and in which order (set in `studio.yaml`, most important first). An issue or roadmap line that serves none of them needs a reason.

1. A room of friends starts and finishes a game from their phones in under a minute, no app and no account, with or without a shared screen.
2. Grow the library of games and licensed content while every screen is designed before it is built and works at phone sizes in English and Hebrew.

## Roadmap

The pinned issue titled `Roadmap` (labelled `roadmap`) is the product agent's view of where this repository is going: a direction paragraph, then `Now` (at most 3 items, each with an issue), `Next` (at most 5) and `Later` (at most 8), what was done in the last 14 days, and open questions for a person. The agent rewrites it on every product cycle and posts one comment saying what moved and why.

- To influence it: comment on the `Roadmap` issue. The agent reads every comment from a person on its next cycle and answers in its own comment.
- To change it directly: edit the issue body. The agent keeps what you wrote and says so; it never deletes a human line without a comment explaining why.
- To take an item away from the agents: label its issue `ready-for-human`. It stays on the roadmap as yours, and no agent works on it until a person decides.
- The committed design docs are inputs to the roadmap, never outputs. The product agent reads them and does not edit them; change them with a pull request as usual.

## What merges without a person

A pull request merges on its own only when QA passed, the lead agent approved it, it changes at most 15 files, and it touches none of: `ios/`, `.github/`, `.githooks/`, `design/`, `docs/designs/`, `scripts/`, `vendor/`, `package.json`, `package-lock.json`, `tools/testflight.sh`, `tools/release`. Everything else waits for a person.

## Outside contributors

This is an open-source project, and outside contributors come first:

- Agents never claim an issue that a person has asked to take, and leave `good first issue` items to outside contributors for 14 days.
- A pull request from a fork gets a written review from the QA agent, which reads the diff and never runs the code. It then goes to `asaf-shitrit`, who decides and merges. The lead agent never merges a pull request from a fork.
